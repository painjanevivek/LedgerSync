# Candidate recovery and migration proof

Run `node scripts/portfolio/run-recovery.mjs` from the repository root. Docker must run locally. The command has no destination argument. It creates two isolated PostgreSQL databases and one isolated Redis container. Every container has a run-specific identity, an immutable dependency image ID, a loopback port, and temporary storage. The normal database is never a restore target.

The first PostgreSQL instance contains synthetic accounts, ownership, funding, a pending funding request, posted transfers, a correction, recovery intents, and approved and pending delivery work. The runner takes an unfiltered owner backup in PostgreSQL custom format. Its separate `ledgersync-isolated-candidate-backup/v1` manifest binds the exact source, ordered migration manifest, checksum, byte count, fixed role identities, currency scope, format, and completion state. This is distinct from the historical normal-stack backup format and its INR scope.

The validator rejects missing or incompatible metadata, an incomplete bundle, a different source or schema identity, unsupported roles or currency, unsafe paths, truncated or corrupt bytes, and an invalid custom-format header. It validates before a new restore target is created. Backups and raw evidence stay in ignored local storage. The 128 MiB bound is for this synthetic qualification profile; it is not a production backup size limit.

The runner creates the fixed non-login role identities, restores the schema and records, checks migration history, and atomically reapplies workload grants before any restricted client runs. The restore test compares the count and canonical row hash of all public tables before it writes anything. It then checks forced row policies, controlled writer ownership and search paths, denied unscoped reads and direct writes, the original replay receipt, a pending recovery intent, and an approved replay. A new restricted financial command must post correctly. The independent exact model and internal reconciliation must agree.

Redis is disposable. The test clears only the recorded test Redis instance and rebuilds customer balances through the approved PostgreSQL read path. Internal negative clearing accounts stay outside customer projections. The real shared worker drains restored work. Exact balances, immutable records and financial invariants are checked again.

The migration stage uses separate temporary databases. It covers the phase-seven local snapshot through migration 000012, the known historical live-room shape, and the immediately preceding ordered candidate migration. Historical version records remain. A real migration transaction creates records and then blocks on an advisory lock. The test cancels that transaction, proves that neither its table nor completion record survived, releases the lock, and retries the unchanged source twice. Exactly one application must remain. Setup retries use the dedicated migration command; serving traffic does not run migrations. An unknown historical schema needs an explicit compatibility repair and is not part of the supported local snapshot claim.

Retention checks preserve final financial evidence and durable command identity while they remove only bounded eligible operational rows. Invalid and failed drills remain separate from passing records. The runner verifies source/index and normal container identities, and removes only its exact disposable targets. The calling phase separately compares the normal financial fingerprint and service health.

The elapsed time starts at backup creation and ends after the complete named recovery and migration validation profile. Restore setup is also reported separately. These are local synthetic measurements. They do not establish a managed recovery time, point-in-time recovery, normal-stack backup freshness, or coverage of later writes.

Use `node scripts/portfolio/verify-recovery.mjs data/portfolio/demo-runs/<run-id>/run-manifest.json --save-summary` after a complete run. The verifier checks every recorded artifact and requires every fixed scenario, preservation check and cleanup result to pass. It archives a bounded public summary and updates the read-only Recovery display. It does not expose backup contents, financial rows, credentials, container IDs or host paths. A new summary does not relabel the source identity of an older run. Summary and documentation updates occur after the measured source snapshot.

The Recovery page keeps three normal-runtime questions separate: current database health, validity of a listed backup, and a successful restore of that exact backup. The candidate proof is a fourth, separately labelled historical result. It cannot make a stale normal backup current. An authorized operator can read the proof and copy a host command; the browser cannot execute a restore.

Repeat this drill against the final schema after R15 and R16. Preserve the current normal environment until the later candidate release and cutover gates are met. No cloud execution is part of this phase.
